## 一、文档间不一致问题

### 1.1 后悔指数算法 — 普通物品权重缺失

**涉及文档**：概要设计 §5.3 vs 详细设计 §3.3.3 vs PRD §5.2 vs PDD §3.3.2

- **概要设计**：普通物品后悔指数公式为 `(闲置归一化 × 0.6) + (评分倒数归一化 × 0.4)`；固定资产为 `(闲置 × 0.4) + (评分 × 0.3) + (净值率 × 0.3)`。
- **详细设计**：`regret_ranker.rs` 的 `regret_index` 函数统一使用 `(评分 × 0.3) + (闲置 × 0.4) + (净值率 × 0.3)`，未区分普通物品和固定资产。当 `net_value_rate = None`（非固定资产）时，`net_factor` 默认为 `0.5`，而非使用概要设计中普通物品的 `0.6/0.4` 权重方案。
- **PRD §5.2**：仅描述了"基于评分、闲置频率和净值折损速度"，未给出具体公式。
- **PDD §3.3.2**：计算因子为"评分、闲置天数、净值折损速度"，未区分普通/固定资产。

**结论**：概要设计定义了两套权重（普通 0.6/0.4 vs 固定 0.4/0.3/0.3），但详细设计代码实现了一套统一公式，用 `net_factor=0.5` 兜底非固定资产。这导致普通物品的实际权重为 `(评分 × 0.3) + (闲置 × 0.4) + (0.5 × 0.3) = 0.3评分 + 0.4闲置 + 0.15固定`，与概要设计的 `0.4评分 + 0.6闲置` 不一致。

**建议**：统一为一套方案。推荐详细设计的统一公式（0.3/0.4/0.3），并修订概要设计 §5.3 中普通物品的权重描述，删除 0.6/0.4 的旧方案，明确说明非固定资产的 `net_factor` 取默认值 0.5。

### 1.2 折旧算法 — 概要设计"日折旧"与详细设计"年折旧"粒度冲突

**涉及文档**：概要设计 §5.1 vs 详细设计 §3.3.1 vs PDD §6.3

- **概要设计 §5.1**：直线折旧描述为"日折旧额 = (购买价格 - 残值) ÷ (使用年限 × 365)"，日粒度计算。
- **PDD §6.3 "折旧跨越闰年/2月"**：规定"每日折旧额 = 年折旧额 ÷ 当年总天数"，即每年根据实际天数（365/366）动态调整日折旧额。
- **详细设计 §3.3.1 代码**：直线折旧使用固定 `total_days = useful_life_years * 365`，不考虑闰年；加速折旧使用 `elapsed_days / 365` 按年迭代，年内按天比例 `days_in_current_year / 365`，也不考虑闰年。

**结论**：PDD 明确要求按当年实际天数调整日折旧额（365 vs 366），但详细设计代码使用固定的 365。概要设计也未提及闰年。

**建议**：需要在详细设计中明确闰年处理策略。两条路线：
- **路线 A（简化）**：统一使用 365 天，不处理闰年，同时修订 PDD §6.3 删除"当年总天数"的闰年描述，改为固定 365。
- **路线 B（精确）**：实现 PDD 的闰年逻辑，在详细设计中增加按年分段计算、每段天数取实际日历天数的实现。

推荐路线 A，理由：折旧是财务模拟而非精确会计，365 天固定值在 5-10 年使用年限下误差极小（≤2.7%），且代码简洁。但需在 PDD 中同步修改。

### 1.4 闲置检测 — "沉默成本"定义冲突

**涉及文档**：概要设计 §5.2 vs PDD §3.3.1 vs 测试用例 TC-M6

- **概要设计 §5.2**：定义"沉默成本 = 购买价格"。
- **PDD §3.3.1 闲置清单**：列表内容含"沉默成本"但未定义其计算方式。
- **数据字典**：无 `silent_cost` 字段。
- **详细设计 export_idle_csv 代码**：输出列含 `silent_cost`，但实际值取 `item.purchase_price`。

**结论**："沉默成本 = 购买价格"过于简化。一个闲置物品的沉默成本应包含购买价格 + 累计维护支出（即总投入），而非仅购买价格。概要设计和代码都只取购买价格。

**建议**：明确"沉默成本"的定义：
- **方案 A**：沉默成本 = 购买价格（简单，当前实现）—— 但命名误导，改为"购买价格"更准确。
- **方案 B**：沉默成本 = 购买价格 + 累计维护支出 = 总投入（更符合"沉默"语义）。

推荐方案 B，并在概要设计、数据字典、详细设计中统一修改。

### 1.5 物品表 `purchase_price` 允许 NULL vs PRD "必填"

**涉及文档**：PRD §5.1 vs PDD §3.2.3 vs 数据字典 §2.3 vs 详细设计 §3.1 DDL

- **PRD §5.1 物品录入**：描述中"价格"似乎是核心字段，未明确标注为可选。
- **PDD §3.2.3 添加/编辑物品**：明确标注"选填字段"含价格。
- **数据字典**：`purchase_price` 必填=否，默认值=NULL。
- **详细设计 DDL**：`purchase_price REAL`，无 NOT NULL 约束，允许 NULL。

1. 修订 PRD §5.1 明确标注"价格"为选填字段。
2. 在数据字典和详细设计中明确约定：前端传入 `null`/不传时后端存储 `NULL`；前端传入 `0` 时后端存储 `0`（0 是合法值，代表免费物品）。删除 PDD §6.1 中"0 视为未填写"的描述，改为"空值时保持 NULL"。

### 1.6 物品表 `purchase_date` — 允许 NULL vs 约束"不早于1900-01-01，不晚于当前日期"

**建议**：统一为 PDD 的方案——允许未来日期，但标注为"未到手"状态。修订数据字典中 `purchase_date` 的约束为"不早于 1900-01-01"，删除"不晚于当前日期"的限制。

### 1.7 品类表 `name` 字段缺失 vs 数据字典预设数据

**涉及文档**：数据字典 §2.1 vs §5 预设数据 vs 详细设计 DDL

- **数据字典 §2.1 categories**：字段只有 `id, key, parent_id`，无 `name` 字段。说明"key 是英文标识，如 'electronics'"，显示名由 i18n 文件映射。
- **数据字典 §5 预设数据**：列有"中文显示"和"English Display"，但标注"多语言映射存储在语言文件中，数据库只存 key"。
- **详细设计 DDL**：categories 表无 `name` 列，与数据字典一致。

### 1.9 3件匹配逻辑 — 详细设计代码缺陷

**涉及文档**：详细设计 §3.2.5 `find_idle_match`

代码中 3 件匹配逻辑为：

```rust
if best_match.is_none() {
    // 3件匹配 ...
}
```

仅在 `best_match` 为 `None`（即 1 件和 2 件都没找到匹配）时才尝试 3 件匹配。但 PRD/PDD 的优先级规则是"件数最少 + 价格最接近"。当前实现忽略了"3 件组合可能比已找到的 2 件组合价格更接近"的情况。

例如：目标 1000 元，2 件组合总价 1050（差 50），3 件组合总价 1010（差 10）。当前代码会返回 2 件组合（因为 2 件先找到），但按"最接近"规则应返回 3 件组合。

**结论**：代码的优先级逻辑是"件数绝对优先，不考虑精度"，而需求文档的优先级是"件数最少 + 价格最接近"，两者对"件数优先"的权重理解不一致。

**建议**：明确优先级规则的精确语义。推荐："在件数相同的情况下选价格最接近的；件数不同时件数少者优先，但不考虑件数多但价格更接近的组合"。当前实现符合此语义，但需在 PRD/PDD 中明确此规则，避免歧义。同时删除 `if best_match.is_none()` 条件，改为在 3 件匹配中也检查价格差，仅在差值更小且件数更少时替换（当前逻辑已隐含此行为，但代码结构不够清晰）。

### 2.3 详细设计 — 加速折旧算法中当年内折旧计算逻辑有误

**涉及文档**：详细设计 §3.3.1 加速折旧分支

代码中处理当年内已过天数的逻辑：

```rust
let yearly_dep = if elapsed_years < switch_to_linear_at {
    (book_value + accumulated - input.purchase_price + accumulated).abs()
        .min(book_value * rate)
} else { ... };
```

表达式 `(book_value + accumulated - input.purchase_price + accumulated)` 即 `(book_value + 2*accumulated - purchase_price)`，这在财务上没有意义。应该是 `(book_value * rate).min(book_value - residual_value)`，即当年双倍余额递减的折旧额不超过账面净值减残值。

**建议**：修正此表达式为 `let yearly_dep = (book_value * rate).min(book_value - input.residual_value);`。

### 2.4 详细设计 — `total_net_value` 计算逻辑有误

**涉及文档**：详细设计 §3.2.3 `get_dashboard_data`

```rust
let mut total_net_value = total_value;
for asset in &fixed_assets {
    total_net_value = total_net_value - result.accumulated + (asset.purchase_price - asset.residual_value);
}
```

此逻辑的含义是：初始 `total_net_value = total_value`（所有活跃物品购买价格之和），然后对每个固定资产减去累计折旧再加回 `(purchase_price - residual_value)`。这等于 `total_value - accumulated + (purchase_price - residual_value)`，结果不符合"净值"的语义。

正确的净值计算应为：
- 普通物品净值 = 购买价格（或当前估值）
- 固定资产净值 = 购买价格 - 累计折旧

即 `total_net_value = sum(普通物品.price) + sum(固定资产.purchase_price - accumulated)`。

当前代码的实际计算为 `sum(所有物品.price) - sum(固定资产.accumulated) + sum(固定资产.purchase_price - residual_value)`，多加了一笔 `(purchase_price - residual_value)`。

**建议**：修改为：

```rust
let mut total_net_value = 0.0;
for item in &all_active_items {
    if item.is_fixed_asset {
        let result = engine.calculate_depreciation(&item, today)?;
        total_net_value += item.purchase_price - result.accumulated;
    } else {
        total_net_value += item.purchase_price;  // 或当前估值
    }
}
```

### 2.8 开发计划 — 分支策略命名不一致

**结论**：详细设计中写 `dev`，实际仓库使用 `develop`，CLAUDE.md 也写 `develop`。

**建议**：统一为 `develop`，修订详细设计 §7.5 的分支策略图。

## 三、缺失内容

### 3.1 数据字典 — `wishes` 表缺少外键定义

**涉及文档**：数据字典 §2.7

`wishes` 表没有定义任何外键，但数据字典 §3 "外键与级联规则汇总"中也没有 wishes → items 的关系。然而，愿望的 `PURCHASED` 决策在业务上应关联到某个物品（购买后转化为物品），当前数据模型未建立此关联。

**结论**：wishes 表独立存在，PURCHASED 后不自动创建物品记录。这是设计选择而非缺陷，但应在文档中明确说明此行为。

**建议**：在数据字典或详细设计中补充说明：愿望 PURCHASED 后不自动创建物品，用户需手动添加。

---

### 3.2 概要设计 — 缺少"当前估值"字段说明

**涉及文档**：概要设计 §4.2 核心实体清单 vs 数据字典 §2.3

- **概要设计 §4.2**：items 主要字段含"当前估值"（隐含在 PRD §5.1 "当前估值等"中）。
- **数据字典 §2.3**：items 表无 `current_value` / `estimated_value` 字段。
- **PDD §3.2.2 物品详情**：成本卡片展示"当前估值（若为普通物品）"。

**结论**：PRD 和 PDD 都提到普通物品的"当前估值"，但数据字典和 DDL 中无此字段。

**建议**：在 items 表增加 `estimated_value REAL` 字段（可选，NULL 表示未填写），并在数据字典和 DDL 中同步更新。普通物品的净值展示为 `estimated_value`（若有）或 `purchase_price`（若未填）。

### 3.3 详细设计 — 缺少 `checkins` 表的外键定义

**涉及文档**：数据字典 §2.5 vs 详细设计 §3.1 DDL

数据字典 §2.5 定义了 `item_id → items(id), ON DELETE CASCADE`。DDL 中也定义了。但数据字典 §3 外键汇总表中已列出此关系。

### 3.5 测试方案 — E2E 工具不一致

**结论**：冷却期计算逻辑未被纳入后端模块结构。愿望冷却的判定逻辑（`created_at + cooling_days <= today`）非常简单，可能不需要独立引擎文件。

**建议**：在概要设计和详细设计的后端模块结构中增加 `engine/cooling.rs`（或命名为 `engine/wish_cooling.rs`），或在 `db/wishes.rs` 中内联冷却判断逻辑，并同步更新模块结构图。
