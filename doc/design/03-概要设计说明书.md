## 2. 系统架构

### 2.1 整体架构

藏珠采用 **Tauri 桌面框架** 的经典进程模型：

```
┌─────────────────────────────────────────────┐
│                  Tauri 壳                    │
│  ┌──────────────┐    ┌───────────────────┐  │
│  │   主进程      │    │    渲染进程        │  │
│  │  (Rust)      │◄──►│   (Web 前端)       │  │
│  │              │IPC │                   │  │
│  │ ┌──────────┐ │    │ ┌───────────────┐ │  │
│  │ │ 数据库    │ │    │ │ UI 组件树     │ │  │
│  │ │ SQLite   │ │    │ │ (React)   │ │  │
│  │ └──────────┘ │    │ ├───────────────┤ │  │
│  │ ┌──────────┐ │    │ │ 状态管理      │ │  │
│  │ │ 文件系统  │ │    │ ├───────────────┤ │  │
│  │ │ (图片等) │ │    │ │ 路由          │ │  │
│  │ └──────────┘ │    │ └───────────────┘ │  │
│  └──────────────┘    └───────────────────┘  │
│                                              │
│  ┌──────────────────────────────────────┐    │
│  │           系统 API (Tauri)            │    │
│  │  文件读写 / 剪贴板 / 通知 / 快捷键    │    │
│  └──────────────────────────────────────┘    │
└─────────────────────────────────────────────┘
```

**进程职责分工**：

| 进程 | 技术 | 职责 |
| :--- | :--- | :--- |
| **主进程** | Rust | 数据库操作、折旧计算引擎、文件管理、备份恢复、WebDAV 同步（V2.0） |
| **渲染进程** | TypeScript + React | UI 渲染、用户交互、状态管理、路由导航、数据格式化 |
| **IPC 桥** | Tauri invoke | 渲染进程通过 `invoke` 调用主进程的 Rust 命令，传递参数与返回结果 |

### 2.2 技术选型

| 层 | 选型 | 理由 |
| :--- | :--- | :--- |
| **桌面框架** | Tauri 2.x | 体积小（<5MB），Rust 高性能，完美契合本地优先 |
| **前端框架** | React 18 + TypeScript | 生态成熟，适合数据密集型仪表盘界面 |
| **UI 组件库** | 自研轻量组件 + Tailwind CSS | 保持设计克制，避免重型组件库的样式污染 |
| **图表** | Recharts 或 Chart.js | 轻量，满足仪表盘占比图与趋势图需求 |
| **状态管理** | Zustand 或 Jotai | 轻量，适合中型桌面应用，无模板代码 |
| **路由** | React Router (内存路由) | 桌面应用无 URL，使用内存模式 |
| **本地数据库** | SQLite (通过 rusqlite) | 单文件、零配置、读写极快，完美匹配本地存储 |
| **图片存储** | 文件系统 (应用数据目录) | 数据库仅存路径引用，图片以 UUID 命名存于磁盘 |
| **国际化** | i18next + react-i18next | 生态标准，支持语言文件热切换 |
| **打包** | Tauri bundler | 生成 .msi / .dmg 安装包 |

```
前端组件 (React)
    │ IPC invoke

    │ 调用
    ▼

    │ 读写
    ▼

    │ SQL
    ▼
```

**关键约束**：
- 前端不直接访问数据库，所有数据操作通过 IPC 命令调用

- 数据访问层仅负责 SQL 执行，不包含业务逻辑

## 5. 关键算法概要

### 5.1 折旧计算引擎

**位置**：`engine/depreciation.rs`

**输入**：购买价格、预估残值、使用年限、折旧方法、购买日期、计算日期

**输出**：累计折旧、当前净值、每日折旧额

**算法策略**：
- 直线折旧：日折旧额 = (购买价格 - 残值) ÷ (使用年限 × 365)
- 加速折旧：前 (年限-2) 年使用双倍余额递减，后两年转为直线
- 维持期：折旧日数 ≥ 使用年限 × 365 时，停止折旧，净值 = 残值
- 每日折旧额精确到小数点后两位，四舍五入

### 5.2 闲置检测引擎

**位置**：`engine/idle_detector.rs`

**输入**：物品最后打卡日期、当前日期、闲置天数阈值

**输出**：是否闲置、闲置天数、沉默成本、闲置期间折旧

**算法策略**：
- 闲置天数 = 当前日期 - 最后打卡日期
- 闲置 = 闲置天数 ≥ 阈值
- 沉默成本 = 购买价格 + 累计维护支出（即总投入，代表闲置物品占用的全部资金）
- 闲置期间折旧 = 日折旧额 × 闲置天数（仅固定资产）

### 5.3 后悔指数计算引擎

**位置**：`engine/regret_ranker.rs`

**输入**：物品评分（1-5）、闲置天数、净值率（固定资产）

**输出**：后悔指数（0-100），越高越后悔

**算法策略**：
- 统一公式：后悔指数 = (评分倒数归一化 × 0.3) + (闲置天数归一化 × 0.4) + (净值率倒数归一化 × 0.3)
- **评分倒数归一化**：(5 - 评分) / 4，评分越低后悔度越高；未评分默认 0.5
- **闲置天数归一化**：min(闲置天数, 365) / 365，闲置越久后悔度越高
- **净值率倒数归一化**：1 - 净值率，净值率越低后悔度越高；非固定资产（无净值率）默认取 0.5
- 后悔指数范围 0~1，最终可乘以 100 映射到 0~100 分

## 6. 数据流

### 6.1 核心数据流：物品录入

```
用户填写表单 → 前端校验 → invoke('add_item', payload)
    → Rust 命令校验 → INSERT INTO items → 生成 UUID
    → 保存图片到文件系统 → 缩略图生成
    → 返回 Item 对象 → 前端更新状态 → 列表刷新
```

### 6.2 核心数据流：仪表盘加载

```
用户打开应用 → invoke('get_dashboard_data')
    → 聚合查询：
        SELECT COUNT(*) FROM items WHERE status='active'
        SELECT SUM(purchase_price) FROM items WHERE status='active'
        SELECT SUM(净值和折旧) ...
    → 折旧引擎批量计算所有固定资产当前净值
    → 返回 DashboardData 结构体 → 前端渲染
```

### 6.3 核心数据流：不买计算器

```
用户输入名称和价格 → invoke('find_idle_items_match', { price })
    → 闲置检测引擎筛选闲置物品
    → 组合枚举找总价相近（±10%）的1-3件闲置物品组合，优先件数最少
    → 对匹配到的固定资产计算累计折旧和净值
    → 返回匹配列表 → 前端对比展示
```

## 7. 国际化技术方案

### 7.1 文案管理

- 所有界面文案置于前端 `i18n/` 目录，JSON 格式，按页面/组件命名空间组织
- 后端返回的错误信息也需国际化：前端通过错误码在本地语言文件中查找对应文案

### 7.2 格式化

- 前端：使用 `Intl.NumberFormat` 和 `Intl.DateTimeFormat`，根据当前语言自动格式化
- 后端：仅在计算时处理裸数字，格式化由前端负责

### 7.3 语言切换

- 用户切换语言 → 前端 `i18next.changeLanguage()` → 所有组件重新渲染
- 无需通知后端，数据库中的品类 key 由前端查找语言文件展示

## 8. 非功能性需求的设计策略

| PRD 需求 | 设计策略 |
| :--- | :--- |
| 10,000 条物品不卡顿 | 前端虚拟滚动（react-window 或 @tanstack/virtual）；后端分页查询，默认每页 50 条 |
| 冷启动 < 2s | 启动时不加载全量数据，仪表盘数据使用预计算；SQLite 使用 WAL 模式加速并发读 |
| 崩溃/断电数据不丢失 | SQLite WAL 模式 + 每次写操作即时 fsync；备份为原子复制 |
| 离线运行 | 所有逻辑在本地完成，IPC 调用不涉及网络；仅同步功能可检测网络状态 |
| 窗口最小 1024×768 | 前端使用 CSS Grid/Flex 响应式布局，低于 900px 时侧栏折叠 |
