## 2. 总体测试策略

### 2.1 测试金字塔模型

藏珠采用经典测试金字塔，强调底层测试的高覆盖率，上层测试只验证关键路径。

```
         ╱    E2E 测试    ╲         少量，核心用户流程
        ╱──────────────────╲
       ╱     IPC 集成测试    ╲       中量，前后端命令通道
      ╱──────────────────────╲
     ╱       组件/单元测试      ╲     大量，业务逻辑与 UI 原子行为
    ╱──────────────────────────╲
```

### 2.2 各层级测试目标与占比

| 层级 | 目标 | 预估用例数量 | 执行环境 |
| :--- | :--- | :--- | :--- |
| L1 单元测试 (Rust + TS) | 验证引擎算法、数据库操作、前端工具函数 | 80+ | 开发者本地 + CI |
| L2 组件测试 (React) | 验证 UI 组件交互、表单校验、状态管理 | 40+ | 开发者本地 + CI (jsdom) |
| L3 IPC 集成测试 (Tauri mock) | 验证前端 invoke → Rust 命令返回完整链路 | 20+ | 开发者本地 + CI |
| L4 E2E 测试 | 验证核心用户场景端到端正确性 | 5~8 条 | CI (Linux 无头) + 手动 (Win/macOS) |

### 2.3 准入准出标准

- **提交前准出**：所有 L1、L2 测试必须通过
- **合并请求准出**：L1、L2、L3 全部通过，新增代码覆盖率达到 80% 以上
- **发版准出**：L1~L4 全部通过，跨平台冒烟测试无阻塞性 Bug

## 3. 测试融入开发流程

本章具体说明测试如何嵌入从编码到发布的每一个环节，让测试方案真正成为开发的一部分。

### 3.1 开发阶段与测试对应

| 开发阶段 | 你在做什么 | 测试如何介入 | 对应测试层级 | 方案章节 |
| :--- | :--- | :--- | :--- | :--- |
| **编码中** | 实现引擎算法、数据库操作、前端组件 | 每完成一个函数/组件，立即运行对应单元/组件测试 | L1, L2 | 4.1~4.3 |
| **每日提交前** | 完成一个功能点，准备 `git commit` | 本地运行全量 L1+L2 测试，全部通过方可提交 | L1, L2 | 7.1 |
| **推送到远程后** | `git push` 到 GitHub | CI 自动执行 L1+L2 测试，失败则邮件/通知告警 | L1, L2 | 7.2 |
| **合并 PR 前** | 提交 Pull Request | CI 自动执行 L1+L2+L3，全部通过才可合并 | L1, L2, L3 | 7.2 |
| **发版前** | 准备发布 V1.0 | 手动执行 E2E 测试 + 跨平台冒烟 + 性能测试 | L4 + 非功能 | 7.3 |

### 3.2 完整开发周期示例（以“愿望清单”功能为例）

假设你要实现愿望清单功能：

| 步骤 | 你的操作 | 测试动作 | 结果 |
| :--- | :--- | :--- | :--- |
| 1. 编写后端逻辑 | 写 `engine/cooling.rs`（冷却期计算） | `cargo test engine::cooling` | 通过，确认冷却天数计算正确 |
| 2. 编写数据库操作 | 写 `db/wishes.rs`（愿望CRUD） | `cargo test db::wishes` | 通过，确认状态流转正确 |
| 3. 编写前端组件 | 写 `WishList.tsx` 和 `BuyCalculator.tsx` | `npx vitest run --reporter=verbose` 运行组件测试 | 通过，确认冷却倒计时显示、决策按钮状态正确 |
| 4. 功能完成本地提交 | 所有代码完成，准备 `git commit` | `cargo test && npx vitest run` | 全量通过，提交 |
| 5. 推送到 GitHub | `git push` | CI 自动运行 Rust + 前端测试 | 绿灯，无告警 |
| 6. 创建 PR 请求合并 | 提交 Pull Request | CI 自动运行 L1+L2+L3（Tauri 模拟集成测试） | 全部通过，代码可合并 |
| 7. V1.0 发版前 | 所有功能集成完毕 | 手动跑 E2E（TC-E2E-003 愿望冷却）+ Windows/macOS 冒烟 | 通过，可发布 |

### 3.3 测试失败的即时反馈机制

| 场景 | 反馈方式 | 你的行动 |
| :--- | :--- | :--- |
| 本地编码时测试失败 | 终端红色错误信息 | 立即修正代码，再次运行测试直到通过 |
| 提交前本地测试失败 | 终端红色错误信息 | 禁止提交，修复后重新运行并通过 |
| CI 测试失败 | GitHub Actions 邮件通知，PR 页面红色叉号 | 查看 CI 日志，修复后重新推送 |
| E2E 失败 | 截图 + 错误报告 | 分析是环境问题还是代码回归，修复后重新触发 |

## 4. 测试层级详细设计

### 4.1 L1-Rust 单元测试

#### 4.1.1 覆盖范围

- `engine/depreciation.rs`：折旧计算引擎
- `engine/idle_detector.rs`：闲置检测
- `engine/regret_ranker.rs`：后悔指数计算
- `db/` 模块的 CRUD 函数（使用内存 SQLite）
- `utils/` 工具函数

#### 4.1.2 测试工具与环境

- **工具**：Rust 内置 `#[test]` + `cargo test`
- **数据库模拟**：`rusqlite::Connection::open_in_memory()` 创建临时库，每次测试前运行 migrations
- **覆盖率**：使用 `cargo tarpaulin` 统计

#### 4.1.3 用例设计规范

每条 Rust 测试函数顶部注释包含：
- 用例编号（如 `TC-ALG-001`）
- 对应的 PRD/详细设计章节
- 测试类型（正常/边界/异常）

示例：

```rust
/// TC-ALG-001 | PRD 5.6.2 | 详细设计 3.3.1
/// 直线折旧法，第2年末净值验证
#[test]
fn test_linear_depreciation_year2() {
    // 价格10000，残值1000，年限5，已过2年
    let input = DepreciationInput { ... };
    let result = DepreciationEngine::calculate(&input);
    assert!((result.accumulated - 3600.0).abs() < 0.01);
    assert!((result.net_value - 6400.0).abs() < 0.01);
    assert!(!result.is_completed);
}
```

### 4.4 L3-IPC 集成测试

#### 4.4.1 方法

使用 **Tauri 模拟运行时**创建最小 App 实例，直接调用 `#[tauri::command]` 函数，验证从命令入口到数据库读写的完整逻辑。

#### 4.4.2 示例

```rust
// TC-IPC-001 | 命令集成测试
#[cfg(test)]
mod ipc_tests {
    use tauri::test::mock_builder;

    #[tokio::test]
    async fn test_add_item_command() {
        let app = mock_builder().build().unwrap();
        // 初始化数据库...
        // 调用 add_item 命令
        let result = add_item(app.state(), payload).await;
        assert!(result.is_ok());
    }
}
```

#### 4.4.3 覆盖重点

- 物品增删改查命令
- 打卡唯一性约束
- 仪表盘数据聚合正确性
- 愿望决策状态流转

### 4.5 L4-E2E 测试

#### 4.5.1 工具

- **框架**：WebdriverIO（官方推荐 + Tauri 社区支持良好）
- **驱动**：
  - Linux CI：`webkit2gtk-driver`
  - Windows 手动：`msedgedriver`（系统自带）
  - macOS 手动：使用 CrabNebula 的 tauri-driver 或纯手动验证

#### 4.5.2 CI 执行方案

在 GitHub Actions 中使用 Ubuntu 镜像，安装 `webkit2gtk-driver` 和虚拟显示器 `xvfb`，运行 E2E 脚本。

```yaml
- name: Install WebKit driver
  run: sudo apt-get install -y webkit2gtk-driver xvfb
- name: Run E2E tests
  run: xvfb-run npx wdio run ./e2e/wdio.conf.ts
```

#### 4.5.3 核心 E2E 场景

| 编号 | 场景 | 关键验证点 |
| :--- | :--- | :--- |
| TC-E2E-001 | 新用户引导流程 | 空仪表盘 → 添加第一件物品 → 详情页展示 |
| TC-E2E-002 | 固定资产全生命周期 | 录入固定资产 → 查看净值 → 打卡 → 闲置检测 |
| TC-E2E-003 | 购物克制闭环 | 添加愿望 → 等待冷却（可缩短配置）→ 决策放弃 |
| TC-E2E-004 | 数据备份恢复 | 备份 → 清空 → 恢复 → 验证数据完整 |
| TC-E2E-005 | 语言切换 | 切换三种语言，遍历页面无遗漏硬编码 |

#### 4.5.4 跨平台 E2E 限制

macOS 和 Windows 的 E2E 由于驱动生态原因，在 V1.0 阶段采用**手动冒烟测试**代替。发版前执行核心场景 TC-E2E-001 至 TC-E2E-003。

## 7. 测试执行流程与 CI 集成

### 7.1 本地提交前

```bash
# Rust 全量单元 + 集成测试
cargo test

# 前端单元 + 组件测试
npx vitest run

# Clippy 静态检查
cargo clippy -- -D warnings
```

### 7.2 GitHub Actions CI 流水线

```yaml
name: Test Suite
on: [push, pull_request]

jobs:
  rust-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Rust tests
        run: cargo test --verbose

  frontend-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci
      - name: Vitest
        run: npx vitest run

  e2e-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install deps
        run: sudo apt-get install -y webkit2gtk-driver xvfb
      - run: npm ci
      - name: E2E
        run: xvfb-run npx wdio run ./e2e/wdio.conf.ts
```

## 8. 测试环境与数据管理

### 8.1 测试数据工厂

在 `tests/fixtures/` 下维护测试数据：

- `sample_items.json`：10 件物品（含固定资产）
- `bulk_10k_generator.rs`：生成 10,000 条伪数据用于性能测试
- `test_backup.zip`：预置恢复测试用的备份文件

### 8.2 测试隔离原则

- 每个测试用例在执行前创建独立的数据库（内存或文件），测试后销毁
- 前端测试 mock 掉所有 `invoke` 调用，不依赖后端运行环境
- E2E 测试每次启动全新的应用实例，使用独立的数据库文件

---

## 9. 缺陷管理与回归策略

- 每发现一个 Bug，首先补充一个对应的单元/组件测试（使其失败），然后修复代码，该测试成为回归测试的一部分
- E2E 测试中的失败可能导致误报（环境波动），需人工确认，两次重试仍失败则开 Issue
